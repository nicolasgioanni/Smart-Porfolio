# Infrastructure adoption sequence

Terraform is inactive. No resource has been imported, applied, or changed by this repository, and no HCP Terraform workspace or remote state has been adopted as evidence. Remote-backend organization/workspace configuration, credentials, provider/API responses, saved plans, state copies, approvals, and inventories belong in an authorized private operational location outside every Git worktree.

Before any separately authorized action, an operator must authenticate to the intended Cloudflare, GitHub, and HCP Terraform services and verify the exact account or repository identity, workspace ID and organization/project membership, local execution setting, state-version ID, lineage, serial, state digest, provider entitlement, resource IDs, and existing control ownership. The absence of that evidence blocks activation. A locally supplied JSON record may help the saved-plan guard compare values; it does not replace authenticated evidence.

Adopt one root at a time. Review and complete preview before production. Import an existing resource only with an exact reviewed ID, then generate a fresh saved plan that is a complete no-op. Bind that plan and its rendered JSON to a clean committed source checkout, the complete root-and-local-module configuration and lock digests, the pinned Terraform binary digest, a private exact-resource inventory digest, and the freshly inspected workspace/state identity. The inventory must bind each physical resource ID and the Cloudflare account or GitHub repository identity before the canonical plan/OPA check can run. Preview Access admission also requires concrete policy IDs: Terraform configuration exports flatten list references and cannot prove their precedence-slot association while IDs remain computed. Immediately before a separately authorized action, refresh the mutable provider, workspace, state, and branch-control evidence and run the saved-plan guard again.

`cloudflare-shared` is blocked until the existing Direct Upload Pages project, full deployment configuration ownership, custom-host coverage, and WAF/rate-limit entitlement are confirmed. `cloudflare-preview` is also blocked until the current preview D1 identity, human custom-host Access application, Pages wildcard ServiceAuth application, adopted service-token ID, and required Cloudflare entitlement are independently reviewed. Terraform must receive only the adopted token ID; client credentials remain in a later protected preview environment and must never enter state, plans, repository files, logs, or artifacts. Neither Access application can be treated as current runtime protection before that separate activation review. `cloudflare-audit` is optional and must not be wired into the Pages runtime unless a later dedicated change adopts its queue, storage, collector, and required provider entitlements. The audit collector's sealed bundle record must be supplied privately for its plan check.

`github-governance` may only adopt the existing single `protect-permanent-branches` ruleset. Confirm that it covers exactly `main` and `develop`, has active deletion and non-fast-forward protection, and has no bypass actor. Do not create a duplicate ruleset, claim GitHub environments exist, or transfer the separate classic `main` pull-request policy into this state.

If any review reports drift, missing entitlement, an unexpected resource, a non-no-op plan, or incomplete evidence, stop. Do not remove secrets, weaken controls, create a replacement resource, change a provider tier, or use import/apply to make preparation appear complete.
